# S3 Resource (Phase 2)

## Why S3, and why this document exists

Phase 1 proved the platform's design (contract → renderer → Terraform
→ plan analysis → platform policy → Checkov → security gate → HITL →
GitHub PR) for exactly one AWS resource type: SQS. Batch 16 (Phase 2)
adds S3 buckets — not because S3 is inherently interesting, but to
prove the same design generalizes to a second resource type without
duplicating the platform. What's shared (HCL-rendering primitives, KMS
key-ID validation, the destructive-change policy, every graph node
except rendering and PR text) and what stays resource-specific (name
validation, encryption/public-access/versioning policy, the Terraform
module itself) is a deliberate design decision — see
`iac_agent.providers.aws.resource` and `iac_agent.providers.aws.renderer`
for the shared `AWSResourceSpec` union and the two-case dispatch that
makes this possible.

## The contract: `S3ResourceSpec`

`iac_agent.providers.aws.s3.contract.S3ResourceSpec` is the S3
counterpart to `SQSResourceSpec` — a strongly typed, Pydantic-validated
model with no network calls, no AWS SDK, no filesystem access:

```python
S3ResourceSpec(
    name: str,
    environment: str | None = None,
    versioning: bool = True,
    encryption: S3EncryptionSpec = S3EncryptionSpec(),
    block_public_access: bool = True,
    tags: dict[str, str] = {},
)
```

### Hard invariants (unconstructible otherwise)

- **Encryption cannot be disabled.** `S3EncryptionSpec(enabled=False)`
  raises at construction — Phase 2 has no representation for an
  unencrypted bucket at all, mirroring SQS's identical encryption
  invariant.
- **Public access cannot be unblocked.** `block_public_access=False`
  raises at construction, for the same reason.

### Soft policy (WARN, not BLOCK)

- **Versioning is recommended, not required.** `versioning=False` is a
  legitimate, constructible configuration — the security gate treats a
  disabled-versioning bucket as WARN, never BLOCK (see
  `S3_VERSIONING_RECOMMENDED` below), mirroring the SQS DLQ policy's
  identical WARN-not-BLOCK precedent.

## Bucket-name validation

Verified against the current AWS S3 "general purpose buckets naming
rules" documentation before implementation (not assumed from training
data or an older tutorial):

- 3–63 characters.
- Lowercase letters, digits, periods, and hyphens only.
- Must begin and end with a letter or digit.
- No two adjacent periods.
- Must not be formatted as an IPv4 address (a shape check — AWS rejects
  this regardless of whether the octets are in range).
- Must not start with a reserved prefix: `xn--`, `sthree-`,
  `amzn-s3-demo-`.
- Must not end with a reserved suffix: `-s3alias`, `--ol-s3`, `.mrap`,
  `--x-s3`, `--table-s3`.

**Global-uniqueness caveat:** a name that passes every rule above is
only *syntactically* valid. S3 bucket names are globally unique across
every AWS account in a partition, and this contract has no way to check
that without a live AWS API call — which Phase 2 deliberately never
makes. A syntactically valid `S3ResourceSpec` can still fail at real
`terraform plan`/`apply` time if the name is already taken elsewhere in
AWS; this is a fundamentally different failure mode from every other
validation rule above, which the contract catches deterministically
and locally.

## The Terraform module: `terraform/modules/s3`

A small, trusted module with a strict security baseline — never a raw
`aws_s3_*` resource block in the renderer's own output, only a `module`
invocation:

- `aws_s3_bucket.this` — the bucket itself.
- `aws_s3_bucket_versioning.this` — `Enabled`/`Suspended` per
  `var.versioning`.
- `aws_s3_bucket_server_side_encryption_configuration.this` —
  unconditional; `aws:kms` when `var.kms_key_id` is set, `AES256`
  otherwise. Unlike versioning, this resource is never optional.
- `aws_s3_bucket_public_access_block.this` — all four block flags
  hardcoded `true`, unconditional, no toggle variable at all.
- `aws_s3_bucket_policy.tls_only` — denies `s3:*` when
  `aws:SecureTransport` is false.

**Explicitly out of scope for Phase 2** (deferred, not forgotten):
website hosting, ACLs, cross-region replication, lifecycle
configuration, object lock, access logging, CloudFront integration, and
event notifications. Each of these is a legitimate S3 feature; none of
them is needed to prove the platform's cross-resource design, and each
adds its own security surface that would need its own review.

Real `terraform fmt`/`init -backend=false`/`validate`/`plan` runs (see
`tests/integration/test_s3_renderer_terraform.py`) confirm the secure
baseline always plans exactly five resources, all creates, no AWS
credentials required.

## Platform policy

`iac_agent.policies.platform.evaluate_platform_policies` dispatches on
resource type (`match spec: case SQSResourceSpec(): ... case
S3ResourceSpec(): ...`) and evaluates three S3-specific policies plus
the one platform-wide policy shared with SQS:

| Policy ID | Outcome |
|---|---|
| `S3_ENCRYPTION_REQUIRED` | PASS (encryption is a hard invariant, so this is defense-in-depth) |
| `S3_PUBLIC_ACCESS_BLOCK_REQUIRED` | PASS (also a hard invariant; CRITICAL severity) |
| `S3_VERSIONING_RECOMMENDED` | PASS if enabled, WARN if disabled — never BLOCK |
| `TF_NO_DESTRUCTIVE_CHANGES` | shared with SQS — evaluated once, resource-agnostic |

## Checkov: a documented scope exclusion, not a suppressed weakness

Running real Checkov (not a mock) against the secure S3 baseline
surfaces exactly four findings, each corresponding precisely to a
feature this batch explicitly deferred:

| Check | What it wants |
|---|---|
| `CKV_AWS_18` | S3 access logging |
| `CKV2_AWS_61` | S3 lifecycle configuration |
| `CKV2_AWS_62` | S3 event notifications |
| `CKV_AWS_144` | Cross-region replication |

This codebase's `CheckovAdapter` maps *every* failed Checkov check to
`PolicyStatus.BLOCK` unconditionally — there is no WARN pathway for
Checkov findings anywhere in this project. Left unaddressed, these four
findings would make it structurally impossible for any S3 request to
ever reach human approval, even though each finding names a feature
this batch was explicitly told not to build.

This was surfaced to the project owner rather than decided
unilaterally (the batch's own instructions required stopping and
reporting here). The decision: add a narrow, explicit
`DEFAULT_SKIPPED_CHECKS` tuple to `CheckovAdapter`
(`src/iac_agent/security/checkov.py`), applied via Checkov's own
`--skip-check` flag, with each entry commented with the exact deferred
feature it corresponds to. This is a documented scope exclusion, not a
suppressed security issue — implementing any of these four features in
a later phase should come with removing its corresponding skip.

## The SecurityGate fix this batch required

`iac_agent.security.gate.evaluate_security_gate` originally hardcoded
its "platform policy evaluation was complete" check to exactly the
three SQS policy IDs — meaning every S3 request would have failed with
`SecurityGateError` before Batch 16 fixed this. The fix: a
`ResourceType`-keyed mapping,
`REQUIRED_PLATFORM_POLICY_IDS_BY_RESOURCE_TYPE`
(`src/iac_agent/policies/platform.py`), and an explicit `resource_type`
keyword argument on `evaluate_security_gate` (defaulting to
`ResourceType.SQS` to keep every Phase 1 call site's behavior
unchanged). `iac_agent.graph.workflow`'s `security_gate` node derives
the correct resource type from the request's own spec via
`resource_type_of`, never a hardcoded default. This, too, was surfaced
to the project owner before being fixed, per the batch's explicit
"PlanAnalyzer and SecurityGate must work unchanged, or STOP and
report" instruction — `PlanAnalyzer` needed no change at all (it only
ever inspects generic `resource_changes`/`actions`, never a resource
spec type), but `SecurityGate` did.

## Workflow integration

`iac_agent.graph.workflow.build_iac_workflow` is the resource-neutral
entry point — an `S3ResourceSpec` flows through the identical eight
nodes an `SQSResourceSpec` does. Only two things are resource-aware at
all: `render_terraform` (selects the S3 renderer and the S3 trusted
module directory via `resource_type_of`) and the PR/commit text in
`source_control` (states `Resource type: s3` and
`feat(iac): add S3 proposal <request_id>`, never SQS's text). Every
other node — `terraform_execute`, `plan_analysis`, `checkov_scan`,
`security_gate` (after the fix above), `approval_gate` — never
inspects the resource type at all.

`build_sqs_workflow` remains a backward-compatible wrapper around
`build_iac_workflow` for existing SQS call sites; new code (S3 or
otherwise) should call `build_iac_workflow` directly.

## Still no `terraform apply`

Nothing about S3 support changes this project's central safety
property: `TerraformRunner` has no `apply` method anywhere, no AWS
mutation of any kind ever occurs, and a GitHub pull request remains the
terminal artifact for an S3 request exactly as it is for SQS.
